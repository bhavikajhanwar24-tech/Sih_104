# F7 — Runtime rule engine and fact assembly

Deterministic evaluation of **ACCEPTED** / **EDITED** rules from the tenant's **ACTIVE**
policy set. PROPOSED and REJECTED rules are never loaded. No script engines, no reflection
over user strings, no eval — closed operators from F6 only.

## What was built

### Rule engine (`com.sentinelvoice.policy.engine`)

| Piece | Role |
|-------|------|
| `ActivePolicyCache` | Caffeine per-tenant cache of immutable `CompiledPolicy`; invalidated on `PolicySetActivatedEvent`; TTL safety refresh |
| `RuleEngine` | `evaluate(tenantId, FactSet)` → `RuleEvaluation`; Micrometer timer `sentinelvoice.policy.engine.evaluation` |
| `ConditionEvaluator` | Kleene three-valued logic (TRUE / FALSE / UNKNOWN) over `all` / `any` / `not` / `fact+op` |
| `FactAssembler` | Directory + relationship + session + FeatureFrame + linguistic + cross-channel + timezone clock |
| `CrossChannelFactService` | Reads `cross_channel_events` → `cross.recentEmailFromSameIdentity`, `cross.recentSmsLinkClicked` |
| `PolicyRuntimeService` | Facade for ingest + simulate + engine status |

**NO_POLICY:** if the tenant has no ACTIVE set, evaluation returns `state=NO_POLICY` (never silently "safe").

**Caller claims:** linguistic facts are `assertedByCaller=true` and mirrored as
`<path>.assertedByCaller` booleans so a verbal claim is never treated as verified truth.

**Score:** `policyScore` = max of fired `scoreBoost`s (default) or sum-with-cap when
`sentinelvoice.policy-engine.score-mode=SUM_CAP`.

**Floor:** `minLevel` (max over fired) is applied as a policy floor on the intervention ladder
(`EvaluationInput.policyMinLevel`).

### Schema

- `V011__policy_engine_timezone_cross_channel.sql` — `tenant_settings.timezone` (default
  `Asia/Kolkata`); `cross_channel_events` with RLS.
- Fact catalogue (+ contract): assertion suffixes + cross-channel facts.

### Pipeline wiring

`FeatureFrameIngestService` rebuilds facts and re-evaluates on every FeatureFrame (linguistic
changes ride the same frame). TRANSACTION fusion score = `policyScore`. v1
`TransactionScoring` / `RelationshipScoring` / `CrossChannelScoring` YAML blocks and
`SentinelProperties.ContextScoring` are **deleted**. Cross-channel is a fact producer, not a
YAML boost formula.

### API

| Method | Path | Auth | Notes |
|--------|------|------|-------|
| POST | `/api/v2/policy/simulate` | ADMIN / APPROVER / ANALYST / AUDITOR | `{policySetId\|active, facts}` → `RuleEvaluation`; `simulation=true`; **not** audited as a decision |
| GET | `/api/v2/policy/engine/status` | same | `{activePolicyVersion, ruleCount, cacheLoadedAt, avgEvalMicros, …}` |

### Frontend

- Policies header **engine status chip**: `Active vN · R rules · loaded Xm ago`.
- **Simulate** tab: fact JSON form, run, fired rules with citations, undetermined rules + missing
  facts, floor level.

## Manual verification

Prerequisites: Postgres through V011, backend `:8081`, frontend `:5173`, an ACTIVE policy set
with ACCEPTED/EDITED rules (from F6).

1. **Engine chip** — open Policies. Chip shows Active version + rule count (or "No ACTIVE policy").
2. **Simulate fire** — Simulate tab → default facts (wire 25L, beneficiary unknown) → Run.
   Expect fired rules, `minLevel ≥ 1`, `simulation: true`, citations when `source` present.
3. **UNDETERMINED** — remove `ask.amountInr` from facts JSON → Run. Expect undetermined rules
   listing `ask.amountInr` and UI copy about rules that could not be evaluated.
4. **PROPOSED ignored** — confirm only ACCEPTED/EDITED appear in `ruleCount` / fire list
   (PROPOSED in a DRAFT set never loads into ACTIVE cache).
5. **NO_POLICY** — tenant with no ACTIVE set → status `NO_POLICY`; live frames do not invent a
   "safe" transaction score (`transactionAvailable=false` / score 0).
6. **Latency** — status `avgEvalMicros` / `lastEvalMicros` populated after simulate; target
   p99 &lt; 2 ms for ~500 rules (local smoke: sub-ms for small sets).
7. **Activation invalidate** — approve a new set → chip version bumps without restart.

## Live Rules addendum

Runtime-facing companion to F6 Live Rules: cache sync, reload, and post-activation check.

### Engine status (extended)

`GET /api/v2/policy/engine/status` now includes:

| Field | Meaning |
|-------|---------|
| `policySha` / `engineSha` | sha256 of compiled ACTIVE rules in cache |
| `databaseVersion` / `databaseSha` / `databaseRuleCount` | ACTIVE set in DB |
| `engineVersion` | version loaded in cache |
| `inSync` / `syncState` | `IN_SYNC` or `MISMATCH` (version + sha + count) |

`POST /api/v2/policy/engine/reload` (TENANT_ADMIN) invalidates Caffeine and warms the ACTIVE set.

Reload also runs after `PolicySetActivatedEvent` (approve of a new set **or** a removal draft).

### UI

- Policies header chip shows **in sync** or **Engine out of sync**.
- **Live Rules** tab: mismatch banner with engine vs database versions + **Reload**; coverage summary; per-rule JSON / Simulate / Delete (removal-draft).
- After approval response includes `engineSync` for post-activation green/red.

### Manual checks (addendum)

8. **Live Rules** — open tab with an ACTIVE set; confirm only ACCEPTED/EDITED rows; Simulate pre-fills facts.
9. **Mismatch** — if sha differs, banner + Reload restores `inSync=true`.
10. **Removal** — Delete on a live rule → draft created; row shows pending; rule still in `ruleCount` until approve.
